# Security review, 2026-10-19 (b)

A review of three additions:
- **Starting a new session by voice:** the `new_session` tool and `desktop.ps1 -Mode new`.
- **Spoken updates while asleep** ("Wake Grok to say it").
- **Reading back a brand-new session.**

It found 11 distinct issues: 2 MEDIUM (one of them older than this change) and 9 LOW, with no CRITICAL or HIGH. No path was found that sends a prompt into Claude without the user's consent. The fixes are below. Testing found six more real bugs, also below. The 2026-10-19 findings were re-checked and none had regressed.

## Method

Three reviewers each read the whole change through one lens:

- **Consent integrity:** can a notification, a transcript, a second-brain answer or a spoken update cause a send, or open the mic longer than promised?
- **Bridge authentication and input handling:** the `/voice?announce=1` socket, the new page messages and events, settings, timers, logs, and the PowerShell arguments.
- **UI Automation safety:** could the wrong window or the wrong control be pressed or typed into?

The UI Automation reviewer checked its claims against the live Claude window (desktop 2.42304, Microsoft Store build). It used read-only inspection only and pressed nothing. Each candidate finding was traced through the exact code. Unsubstantiated candidates were dropped.

Fixes were verified in five ways:
- **Unit tests:** `test/sandboxed/new-session.test.js` and `test/sandboxed/announce.test.js` (new), and `test/sandboxed/tools.test.js`.
- **Fuzzing:** new invariants for new sessions, session switches, send targets and spoken updates. It was run repeatedly until clean.
- **Real end-to-end runs** against the Claude desktop app: "hey are you there" in a new session, sent and read back three times, plus dry runs of every guard.
- **The real Orbit UI:** run in Electron against a fake Grok, measuring when mic audio reached Grok.
- **Real UI Automation tree:** checked against the claims about the window's structure.

## Findings and fixes

### M1. A noise in the spoken update's listening window kept the microphone open with no end (MEDIUM)
**What:** any speech event from xAI inside the 3-second window turned the spoken update into an ordinary conversation, in both the bridge and the page. A cough, a TV or someone else talking was enough. In always-on mode nothing hung up after that.
**Why it matters:** a conversation you never started could stream your microphone to xAI, and be billed, until you said "go to sleep".
**Fixed:**
- Speech that starts in the window only counts once it's transcribed into real words (letters or digits). Until then the bridge forwards audio for at most 8 s more (`heardMs`), then hangs up ("no words").
- A conversation that began as a spoken update hangs up by itself after 20 s of quiet in the page, or a minute while a draft waits for your yes. The bridge enforces 75 s (`idleMs`) as a backstop.
- The update's closing question is now an open one ("what would you like to do next?") rather than a yes/no one.

### M2. Web content shown in Claude's window could stand in for Claude's own controls (MEDIUM, older than this change)
**What:** every UI Automation lookup searched the whole Claude window. That includes web pages Claude shows inside it, such as the Browser pane and previews. Three ways this could go wrong:
- A page titled "… - Claude Code" could supply the session title.
- A focused `<textarea aria-label="Prompt">` could receive a dictated prompt.
- If Claude's own Send was missing, the nearest enabled "Send" anywhere in the window could be pressed, with no distance limit.

**Fixed:**
- `desktop.ps1` first finds Claude's own page: the largest document that contains Claude's sidebar. The Find bar and other web views are separate documents, as checked on the live tree.
- The session title, prompt box, Send button, sidebar buttons, new-session heading and folder are accepted only if their nearest document is that page.
- Send must be on the prompt box's row, within 200 px of its right end.

### L1. `new_session` checked when you last spoke, not what you said (LOW)
**What:** any recent utterance enabled it, for example "what did Claude do?". Text inside the transcript Grok then read could start a new session, which also discards the current draft. Nothing could be sent.
**Fixed:**
- It needs your own words asking for one ("new", "fresh", "another", "start over"), with no "don't" or "no".
- It must come after the latest app notification and the latest second-brain answer.
- One request starts one session.

### L2. `switch_session` had no request check, and spoken updates now read transcripts before anyone speaks (LOW)
**What:** injected text in a transcript read during a spoken update could switch Claude's window, so your next draft would go to that session.
**Fixed:** switching needs something you said in the last 2 minutes, after the latest notification and second-brain answer.

### L3. A draft for a new session wasn't tied to its project folder (LOW)
**What:** the draft was read back as going to "a new session in X", but the send only checked that some new-session page was open. Changing the folder between the draft and the yes would run the prompt in another project.
**Fixed:**
- The draft keeps the folder.
- The send passes `-ExpectFolderB64` and refuses if the page's folder differs.
- Drafting is refused while no folder is chosen.

### L4. The new-session page check could be fooled (LOW)
**What:** any visible text "New session" outside the sidebar counted, including a chat line. No folder was required, and an empty title counted as "no title". `-ExpectNew` could then let a send through to a page that wasn't a new Code session.
**Fixed:**
- Claude's own page must be titled exactly "Claude".
- The heading must be on that page, outside the sidebar and outside any conversation ("Chat messages").
- A chosen "Folder:" is required.
- The title check is `$null -eq $title`.

### L5. Project matching could press the wrong sidebar button (LOW)
**What:**
- A session row titled "New session in …" matched like a per-folder button.
- A substring could match several folders, and the first one won.
- The fallback "New session" button belongs to one sidebar section, not the default folder.

**Fixed:**
- Only buttons that sit directly in the "Sidebar" group count. Session rows sit one level deeper, next to their "More options" button, as checked on the live tree.
- A name that matches more than one folder is refused, with the list returned so Grok can ask.
- The fallback was removed. Only the sidebar's top "New" button is pressed.

### L6. A refused spoken update still connected to xAI (LOW)
**What:** with the setting off or nothing to say, a `?announce=1` socket still opened the xAI connection (sending the key, and billing a moment) before hanging up.
**Fixed:** the bridge checks before connecting to xAI.

### L7. Title cleanup in notifications was incomplete (LOW)
**What:** Unicode line and paragraph separators, other control and format characters, and typographic quotes could break out of the quoted session title in the notification text Grok receives.
**Fixed:** those are all replaced with spaces. This was defence in depth: drafts, new sessions, switches and the second brain all need your own words after a notification.

### L8. The session read-back held up the tool queue, and sidebar folder names went into Grok's instructions (LOW)
**What:**
- `findOpenSession` polled for up to 4 s on the one-at-a-time tool queue, which the Send button also waits on. It kept polling after the connection closed.
- `new_session` put folder names read from Claude's window into `next_step`, the field Grok treats as an instruction.

**Fixed:**
- The wait stops when the connection closes.
- Folder names are only returned as data (`projects`), and `next_step` is fixed text.

### L9. Split view: title and prompt box can come from different panes (LOW, older than this change)
**What:** with two sessions side by side, the title comes from Claude's page while the prompt box is the focused one.
**Status:** partly mitigated. The title now comes only from Claude's own page, and every send still re-checks that title. Documented in SECURITY.md as a known limitation.

## Found by testing

All of these are fixed.

- **Mic audio after a hang-up (fuzzer).** When the bridge refused or ended a spoken update, it cleared its state before the socket finished closing. Mic audio that arrived in that gap was forwarded to xAI. Once the bridge hangs up, everything the page sends is now dropped.
- **The gate opened too late (unit test).** The bridge couldn't hold the mic closed until the page said "this is a spoken update". The page now says so in the socket URL (`/voice?announce=1`), so audio is dropped from the first message.
- **The wrong session read back (real end-to-end test).** Claude gave the new session the same title as an older one ("Are you there"). It also saves a new session's details about 5 s after its first prompt, so the read-back matched the older session by title. After sending a new session's first prompt, Orbit now only accepts a session created since then. It waits up to 10 s, and otherwise says the session isn't saved yet.
- **Sends to a new session refused (real end-to-end test).** The empty prompt box on Claude's new-session page reports its "/" hint as its value. That made it look non-empty, so the confirmation failed and every send would have been refused. A lone "/" now counts as empty. A user who has typed only "/" would lose that one character, which is accepted.
- **Stuck on "Connecting…" (real Orbit UI, older than this change).** A hang-up could leave the orb and status stuck on "Connecting…". The 20-per-second phase timer could overwrite "off" before React re-rendered. It now does nothing once the call has ended.
- **Mistakes in the test tools themselves, not in Orbit.** The fuzzer's `--only voice` never signed in. Its per-round record picked up a previous round's closing socket. Two fuzz runs shared a port. One harness run served a stale UI build. The fuzzer's "secret in a response" check also fired on a key-shaped string the fuzzer had both saved as a key and generated as a fake session title, which isn't a leak. All five were fixed or avoided.

## Measured behaviour

Real Orbit UI in Electron, against a fake Grok that speaks 1.5 s of audio. Times are from the "Claude finished" event:

| | Mic audio first reached Grok | Mic audio last reached Grok | Hung up |
| --- | --- | --- | --- |
| Nothing said | +2.66 s, about 0.9 s after Grok's audio ended | +5.56 s (2.9 s window) | +5.58 s, back to "Sleeping" |
| Words said | +2.55 s | until hang-up | +24.5 s: 20 s of quiet after the words, then "Going to sleep…" |

The page doesn't open the microphone at all until Grok's audio has finished playing and a short chime has played.
